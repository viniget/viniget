Design document · v1 scope

Viniget

Winget has 14,586 packages carrying machine-readable silent-install metadata. Nobody has plumbed that into Wine. Viniget does — for productivity software, on system Wine, with a compatibility database built by actually installing everything.

target Linux + Wine 11.16 catalog 14,155 families scope no games · no Proton status harness validated

Why this is worth building

The insight is not "fetch a manifest and run it." It is that winget manifests already encode how to drive each installer unattended — and that metadata generalises to Wine almost perfectly.

Winetricks hand-maintains roughly 200 verbs. Bottles curates a few dozen installers. Both are human-scale, community-based efforts against a machine-scale problem. The winget catalog is the same information, already structured, already maintained by vendors, and already updated hourly.

The question is what fraction of it Wine can actually drive. Sampling 199 manifests at random and resolving each to its effective installer type:

The part that is genuinely hard

Installing is the easy fifth of the problem. Installing is not running. Nothing in a winget manifest says whether an app works under Wine, and the dominant failure modes are not installer-shaped — they are missing runtimes, WebView2, and .NET. That gap is why the compatibility harness is not an optional extra; it is the product.

Scope decisions

Three calls that define v1. Each one trades reach for a failure rate users can trust.

Productivity, not games
System Wine only. No Proton, no umu-launcher, no DXVK or VKD3D. This removes the entire GPU-translation surface from the compatibility story and makes harness results reproducible across machines. effect · one runner to support instead of a matrix
Standalone tool
Not a Bottles backend or a Lutris source. Viniget owns its prefixes, its index, and its integration path, so the compatibility data has exactly one execution environment to describe. effect · results stay valid; no host-config drift
Never guess for generic exe
A declared Silent or SilentWithProgress switch runs unattended. Without one, viniget opens the installer on the host display and lets the user complete it instead of guessing a flag. measured reach · 11 of 13 exe-only packages sampled already declare a silent mode; the remaining GUI path is supported by the client but excluded from headless compatibility sweeps.

The index is public and unauthenticated

Microsoft publishes the catalog as an MSIX — really a zip — containing a SQLite database, refreshed roughly hourly. Two variants exist, and v1 ships against just one of them:

  • source2.msix — 3.5 MB, v2 schema, 14,586 packages. Fast search. This is the entire download.
  • source.msix — 19.5 MB, v1 schema, adds the pathparts tree of explicit manifest paths. Wired up as a fallback and never actually fetched.

The first sharp edge was found the hard way. measured The CDN does not serve manifests — every path shape returns BlobNotFound; they come from raw.githubusercontent.com.

The second turned out to be a saving. The v1 tree exists to answer "where is this package's manifest", but the answer is a pure function of the identifier and version, so the tree is redundant. measured Derivation was checked against every one of the 164,828 manifest paths in the v1 index, across all versions, not just the latest: 164,828 matched, 0 diverged. That deletes a 19.5 MB download and a 40 MB database from the normal path.

The rule is a convention of the winget-pkgs repository rather than a documented contract, so a 404 falls back to downloading v1 and resolving through pathparts. That path has never run.

Prefixes are copy-on-write

A baseline prefix costs 444 MB to create once. Every install then reflinks from it, which on btrfs or XFS is effectively free and instant. measured Cloning that 444 MB prefix took 0.003s and consumed zero new extents, against 0.158s for a real copy.

That buys three things for about forty lines of code: a genuine rollback point before every install, speculative installs that can be discarded, and per-app isolation at shared-prefix cost. On ext4 the same call degrades to a real copy — slower, still correct.

Installer selection is Wine-aware

Viniget deliberately prefers unattended full installers over archive variants, even though extracting is more reliable. The installer is what registers Start Menu shortcuts, file associations, and icons — the metadata that desktop integration and launch-target discovery both depend on. An unattended archive still beats a generic exe that needs user interaction.

Three rules the harness exists to enforce

Each of these was a wrong assumption in the first prototype. They are the difference between a compatibility database that is useful and one that is actively misleading.

Score on the filesystem, not the exit code

WinMerge's Inno installer ran past a 240-second timeout — having already written 337 files and 8 executables correctly. A harness that trusts the return code records a working application as broken and poisons the database.

Install status is derived from the filesystem delta. The return code is a weak hint, and timeout-but-installed is a pass.

Take the launch target from the Start Menu shortcut

Matching the package name against executables on disk picks WinMerge32BitPluginProxy.exe over WinMergeU.exe. Every one of the five validation packages dropped a .lnk naming its real entry point.

So viniget ships an MS-SHLLINK parser. It feeds two consumers at once — what the harness launches, and what goes into the generated .desktop file. Archive packages have no shortcut; their entry point comes from NestedInstallerFiles in the manifest instead.

Outcomes are three-way, not pass/fail

Greenshot maps zero windows and is entirely healthy — it is a tray application. Binary scoring writes off every background utility in the catalog.

A probe resolves to window-mapped, alive-headless, or died. The first two are both usable.

The default silent-switch table is load-bearing rather than a convenience. measured Only 29 of 199 sampled manifests declare a Silent switch — the rest assume the client already knows how to drive their installer type. Three of the five installs above succeeded purely on viniget's built-in defaults. Declared-silent generic exe packages can join the same sweep; GUI-only packages such as IrfanView stay out because a headless harness has no user to complete them.

The compatibility database

Bundled into the index download. One fetch, one version number, no second staleness axis to reason about.

Compatibility ships as a table inside the same SQLite the client already downloads for search. A user who has an index has a compat database by definition, and viniget search can show a verdict inline without a second network call. The cost is that compat data is only as fresh as the last index build — acceptable, because verdicts change far more slowly than the catalog does.

Why "productivity" cannot be a tag filter

The obvious approach fails. measured The index carries 20,946 distinct tags for 14,586 packages — author-supplied, uncontrolled, and multilingual. The productivity tag covers 195 packages. The top tags are noise: gecko, quantum, and 火狐 all sit near 310 because Firefox ships 310 locale packages and Thunderbird 135.

So viniget does not define "productivity" taxonomically. The harness defines it. "Installs and maps a window under Wine" is a sharper and more honest filter than any category tree, and it is the one users actually care about. Seeding excludes locale forks, MSIX/APPX, and CLI-only packages; measured results do the rest. Collapsing locale forks alone takes 14,586 packages down to 14,155.

The fold has to be narrow to be worth anything. measured The obvious key — the first two dot-segments of the identifier — merges 699 groups of genuinely distinct products, collapsing all 60 Microsoft.DotNet.* packages into one entry, along with 33 Azul.Zulu.* and 26 EclipseAdoptium.Temurin.* variants. So viniget folds X.Y into X only when X is itself a package, Y is a known language subtag, and the display name is tagged with that subtag — "Mozilla Firefox (af)". That fires on exactly 5 families, all Mozilla, folding 431 packages with no false positives.

Sweep economics

At roughly 60 seconds per package including download, install, and probe, a full sweep of 14,155 families is about 15 hours across 16 parallel workers. A GitHub Actions matrix on a public repository does this for free, sharded fifty ways.

Compute is not the constraint — bandwidth is. At an average of roughly 20 MB per installer, a full sweep pulls about 280 GB from vendor servers. So viniget never does full sweeps: packages are retested on manifest-version change only, prioritised by popularity, and nothing is mirrored or cached. Storage is a non-issue, since each test reflinks the baseline prefix and deletes it afterwards.

Build order

Deliberately sequenced so the harness only starts once install is reliable enough that failures are signal rather than noise.

Steps one through three are a working tool on their own. The index client is pure metadata and shipped before a single line of Wine code existed. Step four only pays off once the failure rate is low enough that a died verdict means the application is broken rather than that viniget drove the installer wrong.

Implementation

Go for the client: a single static binary, and SQLite, YAML, and HTTP are the entire workload. Both dependencies are pure Go — modernc.org/sqlite and gopkg.in/yaml.v3 — so nothing pulls in cgo. The harness stays in Python: it is CI-side, iterates constantly, and gains nothing from compilation. A Wails GUI later reuses the Go core.

Open questions

  • Runtime provisioning. WebView2 and .NET are the dominant real-world failure modes and neither is solved by installer automation. Does viniget map WindowsFeatures and PackageDependencies onto winetricks verbs, or report the gap and stop?
  • Opt-in outcome reporting. Real installs on real machines are far better signal than a CI container. Worth the privacy surface, or does CI-only data suffice?
  • WineHQ AppDB cross-reference. Existing ratings would seed the database for the popular tail, but matching winget IDs to AppDB entries is fuzzy.
